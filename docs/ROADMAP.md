# Feature roadmap and implementation boundaries

TypeScript and Three.js remain the supported application stack. The requested Rust rewrite has been dropped; existing experimental Rust code is historical/opt-in, not a migration commitment or production default.

## First delivered slice: project archives

`.LCMX` v1 is a ZIP containing a single `project.txt` entry with the existing 5.1 project representation. It retains component settings, programs, worker data, deduplicated embedded model/animation source files and material texture overrides. ZIP compression reduces repeated text/base64; actual savings depend on asset type. The archive is not a native Visual Components file. Existing `.txt` and `.json` import and `.txt` export remain available.

Save offers a file picker where supported, then autosaves to that selected file while permission is granted. Other browsers download an `.lcmx` copy; they cannot silently update that downloaded file. Import through a file input does **not** attach a writable file handle; use Save and choose a destination again. Browser sandboxes do not allow the application to create or select a default folder in an arbitrary local Larp directory. Browser storage autosave remains separate. Archive compression is synchronous and can temporarily use significant CPU/memory for large assets; 180 MB uncompressed limit applies. Archives with extra files, ZIP64, encryption, data descriptors or a nonmatching checksum are rejected. Treat executable robot scripts in imported projects as untrusted: existing confirmation remains in place.

## Viewport signal editing (V3 prerelease 1)

A viewport toggle exposes OUT markers on visible unlocked buttons, sensors, lasers, PLCs and robots and IN markers on visible feeders, robots, conveyors and PLCs. Signal connections support multiple sources and destinations, undo and archive persistence; the first destination remains in `connectedTo` for old project compatibility, with additional targets on the item. Selection, drag-to-connect, rerouting and individual disconnection are supported; for a shared IN, select its source first. These are not physical robot-controller I/O or material-routing ports. A wired active feeder emits one part per rising source signal (subject to its interval, output clearance and supply); an unwired feeder remains automatic. Direct robot inputs queue rising edges for visual-program picks and scripts using `robot.waitForSignal()`. Robot OUT can pulse after a successful place or indicate moving/holding. These do not implement physical robot-controller I/O or full 3D material-flow editing.

## Deferred roadmap (paused during V3 polish)

1. **Factory topology:** extend the implemented conveyor-merge routing to fan-out/splitters with explicit port types and deterministic product handling; make graph and viewport connections editable, add pallet outputs and pallet transport. Cover disconnected components, branching, flow and save/load in tests.
2. **Workpieces and assemblies:** imported scene models can already be used in feeder, machine and pallet product pickers. Add independent reusable product assets, part attachment, placement compatibility and completed assembly reuse/export before coupling these to the generator. Define failure behavior for missing/mismatched parts.
3. **Scene context and library:** build a versioned catalog index from authorized user-provided Visual Components libraries, retaining original hierarchy, identifiers, properties and source provenance. Investigate a Visual Components add-in and an interchange format for splines/components with round-trip tests in an actual licensed installation. This repository does not contain the full VC library and Construct is not a VC library; reconstructing proprietary models/properties or claiming compatibility without source data and permission is not possible. [Construct](https://github.com/rtmandreyev/construct) describes structured models/parts and glTF export and is Apache-2.0; investigate its contracts and licenses of any individual assets before integrating or redistributing anything.
4. **Robot programming:** create a controller-independent motion and I/O intermediate representation, capture a run with frames, tool/base definitions, velocities, I/O, sensors and subprograms, then implement controller/version-specific KUKA and FANUC generators and parsers with verified fixtures. Simulated code must never be represented as safe to run on hardware without manufacturer-specific validation, real cell calibration and safety review. No controller import/export exists yet.
5. **Object properties and rendering:** build on the fixed-step dynamic/kinematic solver and oriented proxy colliders with continuous collision detection, more detailed geometry, articulated mechanisms and more accurate tilted operations. Add material tags and mass/density estimates with explicit assumptions, then procedural material graphs and particles without changing unrelated rendering presets.
6. **Workers, sensors and interoperability:** add true multi-floor navigation and ledge avoidance, expand worker tasks and rig-safe animation import, sensor-aware generation and procedural sensor wiring; improve external workpiece licensing/provenance and offline fallback. Ensure generated configurations run through the same simulator rules as hand-built scenes.
7. **Multiplayer:** specify local/online authority, conflict resolution, permissions, security and persistence before building synchronization; browser peer connectivity may require signaling or a service.

Each milestone needs behavior tests, representative browser/graphics checks, release notes and explicit gaps. This is a sequence, not a claim that the rest of the roadmap is implemented.
